# QED Script 解説:seL4 の上で「信用しないコード」を安全に動かす

QED Script は QEDOS(seL4 + Microkit 上の HTTPS サーバ OS)に追加した、**サーバ側 WebAssembly 実行基盤**です。
署名された小さな Wasm モジュールを、専用の保護ドメイン(Script PD)の中で、権限を絞って実行します。

この記事では、何を作ったか、なぜそういう設計にしたか、そして**何がまだ保証されていないか**を説明します。
最後の点は特に重要なので、先に書いておきます。

> **この記事の方針**
> テストが通ったことと、性質が証明されたことは別物です。
> 以下では「テストで確認した」「ツールで検査した」「形式的に証明した」を区別して書きます。
> 「証明済み」と書いてあるものは、その範囲が限定されています。

---

## 1. 何ができるのか

```
GET /script/hello   →   {"message":"Hello from QEDOS"}
POST /script/json-echo  (JSON を受け取って加工して返す)
```

- `/script/<name>` に来たリクエストを、署名済みの Wasm モジュールが処理します。
- TLS 1.3 + X25519MLKEM768(ポスト量子ハイブリッド)は従来どおり必須です。
- Script 機能は **opt-in**(`QEDOS_SCRIPT=1` でビルドしたときだけ有効)です。既定のイメージは変わりません。

QEMU 上の seL4 で、PQ-TLS 経由の `GET /script/hello` が正しい応答を返すところまで確認済みです。

## 2. 全体構成

```
        Internet
           │  TLS 1.3 (X25519MLKEM768)
     ┌─────▼─────┐
     │  tls/http │  ← TLS 秘密鍵はここだけ
     └─────┬─────┘
           │ 共有メモリ + notification
     ┌─────▼─────┐
     │ policy_pd │  ← ルーティングと衛生チェック(既存の pg-policy を再利用)
     └─────┬─────┘
           │ /script/* だけ
     ┌─────▼─────┐
     │ script_pd │  ← Wasm インタプリタ。ここに秘密は一切置かない
     └───────────┘
```

ポイントは 3 つです。

1. **Script PD は別の保護ドメイン**です。seL4 のケイパビリティで、触れるメモリとチャネルが静的に決まっています。
   TLS 秘密鍵のメモリは、そもそも Script PD にマップされません。
2. リクエストは **policy_pd を必ず通ります**。既存の HTTP 衛生ルール(パス正規化、ヘッダ検査など)がそのまま効きます。
3. Script PD は **ネットワークにもディスクにも直接触れません**。出口は共有メモリ越しの応答だけです。

## 3. Wasm インタプリタ(`crates/pg-script`)

Wasmi のような既存実装は採用せず、**自前の小さなインタプリタ**を書きました。

| 項目 | 内容 |
|---|---|
| 言語 | Rust、`#![no_std]`、`#![forbid(unsafe_code)]` |
| メモリ | ヒープなし(固定長バッファのみ) |
| 命令 | i32 中心のサブセット(浮動小数点、SIMD、スレッド、WASI、JIT はなし) |
| 実行制限 | **燃料(fuel)** で命令数を制限 |

採用しなかった理由:Wasmi 2.0.0 は `no_std` でビルドできましたが、約 4.3 万行・`unsafe` を含み・アロケータが必要です。
QEDOS の「信頼するコードを小さく保つ」方針に合いませんでした。
代償として、**サブセット外の Wasm(Rust/TinyGo の通常の出力など)は拒否されます**。現時点では手書きに近いモジュールが前提です。

### ホスト API は 8 個だけ

Wasm から呼べる関数は許可リストで固定です。システムコール相当のものは公開していません。
モジュールごとの `.policy` ファイルが、その 8 個のうちどれを使ってよいかを宣言します。
宣言していない API を import するモジュールは、**ロード時に拒否**されます。

## 4. 署名:Ed25519 によるコード署名

配布物は 3 ファイルです。

```
app.wasm     コード本体
app.policy   使ってよい API・資源上限などの宣言
app.sig      Ed25519 署名
```

署名対象は、ランタイム識別子・policy・wasm の SHA-512 などを**長さ付きで連結**したメッセージです
(曖昧さのない連結にして、境界をずらす攻撃を避けています)。

- 検証は **パースより前**に行います。署名が合わないバイト列は、構文解析すらされません。
- コード署名鍵は、TLS 鍵・設定署名鍵とは**別**です。
- 署名は「誰が承認したか」を示すだけで、「そのコードが安全か」は示しません。

> ⚠️ リポジトリには**開発用の署名シード**がコミットされています(再現性のため)。
> 本番利用前に必ず鍵を差し替えてください。

## 5. リソース制限

`.policy` で宣言し、プラットフォーム側の上限で**切り詰め**ます(モジュールが上限を引き上げることはできません)。

- 燃料(命令数)
- 線形メモリのページ数
- 応答サイズ、ホスト API 呼び出し回数 など

超過した場合は、そのリクエストだけが失敗します。他のリクエストや `/health` は影響を受けません。
QEMU 上で暴走ループ(無限ループ)を実行している最中でも、`/health` は約 0.09 秒で応答しました。

## 6. 新しい LAW(LAW_013〜022)

既存の LAW_001〜012 は変更せず、`docs/LAWS.md` に 10 個を追加しました。各 LAW は 8 項目で記述しています。

| LAW | 内容(要約) |
|---|---|
| 013 | メモリ隔離 |
| 014 | ケイパビリティの非昇格 |
| 015 | ホスト API の閉じ込め |
| 016 | 資源の有界性 |
| 017 | 終了制御 |
| 018 | 鍵の非開示 |
| 019 | リクエスト状態の隔離 |
| 020 | 署名済みスクリプトのみ実行 |
| 021 | ストレージのアクセス制御 |
| 022 | バックエンドネットワークの隔離 |

LAW は「守るべき約束」であり、**全部が証明済みという意味ではありません**。各 LAW にどこまで根拠があるかは次節のとおりです。

## 7. 何をどこまで検証したか

検証の強さで 4 段階に分けます。

### (A) 機械的に証明したもの(範囲限定)
- **Kani**(Rust のモデル検査)7 本のハーネス:インタプリタの境界チェック、policy の上限切り詰め、KV キー名前空間の性質など。cover チェックで「前提が空虚でない」ことも確認。
- **Z3**(SMT):範囲チェックの健全性、KV キー連結の単射性。
  対照として、わざと壊した式では反例が出ること(sat)も確認しています。

Kani の結果は**そのハーネスの境界(ループ展開数・入力サイズ)の内側**でのみ成り立ちます。

### (B) ツールによる構成の検査
- `scripts/check-script-caps.py`:ビルドされたシステム記述から、Script PD が持つメモリマップ・チャネルを監査。
  9 個の変異体(わざと権限を足した構成)をすべて検出できることを `--selftest` で確認。

### (C) テスト
- Rust 単体テスト 36、スクリプト機能テスト 16、**敵対的モジュール 36 種(151 アサーション)**、QEMU 上の seL4 での統合テスト 9。
- 敵対的モジュールの例:範囲外メモリアクセス、無限ループ、巨大メモリ要求、未宣言 API の import、不正な署名・改ざん。
- クラッシュ注入:Script PD を意図的に落としても、他の PD が影響を受けないことを確認。

テストは「見つけた範囲では破れなかった」ことしか言えません。

### (D) 証明の「受け皿」だけ作ったもの
- `app.proof`(証明添付)の形式(QSPF1)は定義しましたが、**独立したチェッカがまだありません**。
  そのため `proof_accepted()` は常に `false` を返し、`app.proof` は**安全性の根拠として一切使われません**。
- Viper 用の `.vpr` は生成し、パターン検査まではしていますが、**Viper 自体は実行していません**。

## 8. 性能

| 環境 | 結果 |
|---|---|
| ホスト上のランタイム(hello) | 約 18 万 req/s(約 5.6 µs/件) |
| ホスト上のランタイム(json-echo 1000B) | 約 2,700 req/s(約 373 µs/件) |
| seL4 / QEMU(TCG エミュレーション)`/health` 中央値 | 約 83 ms。Script なしの基線と**差は計測できず** |

注意:

- seL4/QEMU の数字は**ソフトウェアエミュレーション**上のもので、実機の性能を表しません。
- ホスト数値と seL4 数値は別物として扱ってください。比較するものではありません。
- C10K の再実行では 7 項目が合格、1 項目(PERF_008)が不合格でした。
  原因はテスト環境の Python が使う OpenSSL 3.0.2 では X25519MLKEM768 を話せず、
  プローブが 0 件だったためで、プロキシのソースは変更していません。

## 9. 既存機能への影響

- 既存の単体テスト(pg-config 3 / pg-http 21 / pg-policy 6)と seL4 テスト `SEL4_001–006`(6/6)は、
  変更前後ともに通っています。既存の Kani も引き続き通っています。
- `test_tls.py`(7/11)などは、この環境のシステム OpenSSL が古く X25519MLKEM768 に対応しないため、一部が実行できません。
  これは環境起因で、今回の変更による退行ではありません。
- シェルも SSH も追加していません。

## 10. 既知の限界(正直なリスト)

重要なので省略せずに書きます。

1. **壁時計時間の上限がありません**(seL4 側は燃料のみ。タイマクライアント未実装)。
2. **Script PD が死んでも自動再起動しません**。他の PD は無事ですが、`/script/*` は復旧しません。
3. **認証・主体(principal)の概念がありません**。そのため seL4 上では KV(キー値ストア)は常に拒否されます。
   **独立した Storage PD もまだありません**(KV の実装は script_pd 内にあります)。
4. **証明チェッカがありません**。`app.proof` は信用されません。
5. Ed25519 と SHA-512 の実装は**形式検証されていません**。
6. 開発用署名シードがリポジトリにあります(本番では要差し替え)。
7. ロールバック(古い署名済みモジュールへの差し戻し)への対策がありません。
8. Rust / TinyGo の SDK や JS 風 API はありません。通常のコンパイラ出力はサブセット外で拒否されます。
9. Wasmi との**差分テスト(differential testing)をしていません**。インタプリタの意味論の正しさは、自前のテストと Kani の範囲でしか確認できていません。
10. aarch64 向けの Script イメージはビルドしていません。

## 11. 次にやるべきこと(優先度順の案)

1. 認証(principal)の導入と、独立した **Storage PD** への KV 切り出し
2. script_pd にタイマを持たせ、壁時計上限と**自動再起動**を実現
3. Wasmi を参照実装にした**差分ファジング**、および SDK 出力に対応するための命令サブセット拡張
4. 最小の**証明チェッカ**(まず HostApiSubset と FuelBounded から)
5. Viper の実行、署名鍵のローテーション運用

## 12. 試してみる

```bash
# Script 付きイメージのビルド(出力: build/sel4-script)
QEDOS_SCRIPT=1 scripts/build-sel4.sh

# テスト
python3 tests/test_script.py
python3 tests/test_script_security.py
python3 tests/test_script_sel4.py          # QEMU 上の seL4

# ケイパビリティ監査
python3 scripts/check-script-caps.py --selftest
```

詳細は `docs/QED_SCRIPT.md`(使い方)、`docs/SCRIPT_SECURITY.md`(脅威モデル)、
`docs/SCRIPT_VERIFICATION.md`(検証の範囲)、`docs/SCRIPT_RESULTS.md`(結果)を参照してください。

## まとめ

- QED Script は、**署名済みの小さな Wasm を、秘密を持たない別 PD で、燃料とメモリ上限つきで実行する**仕組みです。
- seL4 のケイパビリティにより、Script PD から TLS 秘密鍵・ネットワーク・ディスクへ到達する経路は構成上存在しません(構成監査と QEMU テストで確認)。
- 一方、**壁時計上限・再起動・認証・Storage PD・証明チェッカは未実装**です。「形式的に安全」と言える範囲は、Kani と Z3 が扱った個別の性質に限られます。

「小さく作り、確認できたことだけを主張し、できていないことを明記する」ことを、この機能の設計方針にしました。
