# QEDOS Press — wiring a real production Ed25519 key into `qedos_press_pd`

This closes the gap documented in `docs/QEDOS_PRESS_ADMIN.md`: until now, `qedos_press_pd`'s
actual trust key (`PRESS_PUBLIC_KEY`, compiled into `sel4/rust_press/src/lib.rs`) was a hardcoded
constant, completely independent of whatever public key `tools/press-admin.py`'s host-side
pre-check verified a bundle against. A bundle that passed the host-side check could still be
rejected by the booted image itself, because the two layers trusted different keys. This also
means: until this fix, there was no way for a genuinely new production keypair to actually be
honored by the live, running service at all — this was blocking, not cosmetic.

**Absolute constraint respected throughout this work**: this host never generates, displays,
logs, stores, or transmits any production private key. Every key used while building and testing
this feature is a throwaway TEST keypair, generated by `tools/press-sign-offline.py` into a
scratch directory, never printed in full, never treated as real. The user generates the actual
production keypair themselves, on their own separate machine — see "What the operator does" below.

## The ten requirements, and how each is met

**1. The dev public key must not be used in production builds.**
`sel4/rust_press/src/press_pubkey.rs` is regenerated by `scripts/build-sel4.sh` on *every*
`QEDOS_PRESS=1` build — not just when a production key is requested. By default it's written
with the dev key (so a leftover production key from an earlier local build can never be silently
reused by a later non-production build). When `QEDOS_PRESS_PROD=1` is set, it's written with the
production key instead — and the dev key specifically is refused in that mode (requirement 3).

**2. The production public key must be explicit at build time, and host-side/seL4-side must
agree on the same key's fingerprint.**
`QEDOS_PRESS_PROD_PUBKEY` (env var, defaults to `config/keys/qedos-press-prod-pub.hex` — the exact
same path `tools/press-admin.py --pubkey-file` already defaults to) is the one file both sides
read. `tools/press-admin.py`'s `accept_bundle()` now builds with `QEDOS_PRESS_PROD=1` and
`QEDOS_PRESS_PROD_PUBKEY` set to the *same* `pubkey_hex_file` it just verified the bundle's
signature against — the two layers trust the identical bytes by construction, not by convention.
For an independent, visible cross-check (not just "same file path, trust me"):
`scripts/build-sel4.sh` prints `sha256(pubkey)` during the build; `tools/press-admin.py
--show-pubkey-fingerprint` prints the same thing for whatever file it's configured with; the
`/inbox` page also shows this fingerprint. `tests/test_press_prod_key_sel4.py`'s PROD_010 asserts
these two independently-computed fingerprints are byte-identical for the same key.

**3. Production builds must never fall back to the dev key.**
`scripts/build-sel4.sh` compares the production pubkey's raw bytes against
`config/keys/qedos-press-dev-pub.hex`'s bytes and **hard-fails** (exit 1, no image produced) if
they're equal — PROD_003 proves this.

**4. Unset / malformed / mismatched public key → fail closed (build or boot refuses).**
Three concrete failure modes, all tested (PROD_001/002/003): `QEDOS_PRESS_PROD=1` with no
`QEDOS_PRESS_PROD_PUBKEY` file present; a `QEDOS_PRESS_PROD_PUBKEY` file that isn't exactly 64 hex
characters; a `QEDOS_PRESS_PROD_PUBKEY` identical to the dev key. All three exit non-zero with a
clear message, before any compilation of the real pubkey into anything. On the *boot* side,
`qedos_press_pd`'s existing `pg_press_init`/`verify_and_load` (unchanged by this work) already
fails closed on any signature mismatch — PROD_005/006/007 exercise this directly against the
booted image.

**5. Tamper-evidence / root of trust for the build artifact.**
`scripts/build-sel4.sh` (in `QEDOS_PRESS_PROD=1` mode) performs a **build-time self-check**: after
the final `loader.img` is produced, it greps the actual embedded pubkey bytes out of that exact
file and asserts they match the `QEDOS_PRESS_PROD_PUBKEY` input — this catches a real, plausible
failure mode (a stale cached build of the tiny `pg-sel4-press` crate silently keeping an old key),
not just a hypothetical one; the build also forces `rm -rf sel4/rust_press/target` before
recompiling in this mode specifically to prevent that staleness. It then writes
`$OUT/BUILD_PROVENANCE.txt`: the pubkey fingerprint, a sha256 of the final `loader.img`, a build
timestamp, and the git commit it was built from. **This is a build record for operator review,
not a cryptographic secure-boot or attestation chain** — see requirement 10.

**6. The generation (sequence) number must not be rollback-able by a reboot or image rollback.**
The generation check lives entirely in `tools/press-admin.py`'s `check_and_bump_generation()`
against a small, non-secret, host-local state file (`config/local/press-admin-last-generation`).
This is a **host-side file**, not guest state — the seL4 image itself has no persistent storage at
all and cannot remember anything across a reboot by design (that's not a limitation introduced
here; it's the existing architecture). PROD_009 proves this file survives a simulated
press-admin.py restart (a fresh process re-reading the same file) and still rejects the same old
generation afterward. **Chosen semantics, explicit**: a bundle's generation must be *strictly
greater* than the highest ever accepted — re-deploying the exact same already-accepted generation
number is also rejected (PROD_008), even unchanged. This is deliberately the simplest, least
ambiguous rule: it never requires comparing content hashes to decide whether a generation number
is being safely reused, so there is no subtle case where "the same number but different bytes"
could be waved through. The cost is operational, not security: redeploying unchanged content after
a crash requires bumping the generation number, every time.

**What this does NOT prevent** (said plainly, because the user asked specifically about "image
rollback"): if an old `loader.img` file is booted *directly*, bypassing `press-admin.py` entirely
(e.g. an operator or attacker with host access just runs the old file), nothing in this design
stops that. The generation check only guards `press-admin.py`'s own accept-and-build pathway, not
raw image-file deployment outside it. There is no mechanism in this project that makes an old,
otherwise-valid `loader.img` refuse to boot on its own.

**7. QEMU test matrix: correct / invalid / old / different-key / dev-key signatures.**
`tests/test_press_prod_key_sel4.py`, PROD_001 through PROD_010 (see its module docstring for the
full list). Notably PROD_005/006/007 test the *booted image itself* rejecting a corrupted
signature, a validly-signed-by-a-different-key bundle, and a dev-key-signed bundle respectively —
this is `qedos_press_pd`'s own Ed25519 check, not the host-side pre-filter, which is the point of
requirement 8 below.

**8. Which layer makes the final authorization decision?**
`tools/press-admin.py`'s password+TOTP login decides *who* may attempt a deploy.
Its generation check decides whether a bundle is *allowed to be attempted* — a fail-fast
convenience for the operator, not a security boundary in itself. **`qedos_press_pd`'s own Ed25519
verification, running inside the capability-isolated, formally-verified seL4 image, independent of
and never trusting the host-side tool, is the actual final, authoritative, fail-closed decision on
content authenticity.** If `press-admin.py` were bypassed entirely — someone with host access
hand-assembles a `.press_bundle` section and injects it directly, skipping the admin tool and even
`scripts/build-sel4.sh`'s own checks — `qedos_press_pd` would still refuse to serve content that
doesn't verify against its own embedded key, because `pg_press_init` is a fail-closed check with
no bypass. PROD_005/006/007 prove this empirically: a bad bundle is rejected by the *booted image*
in all three cases, not merely by a host-side tool that could in principle be circumvented.

**9. Don't weaken existing QEDOS / QED Script properties.**
`tests/test_sel4.py` (6/6) and `tests/test_script_sel4.py` (11/11) were re-run from scratch,
unchanged, and pass — these builds never set `QEDOS_PRESS`/`QEDOS_PRESS_PROD` at all, so they are
structurally untouched by this work. `tests/test_press_sel4.py` (8/8),
`tests/test_press_concurrent_sel4.py` (3/3), and `tests/test_press_compat_sel4.py` (5/5) — none of
which use `QEDOS_PRESS_PROD=1` — were also re-run unchanged and pass, confirming the default
(non-production) path is byte-for-byte the same dev-key behavior as before this change.

`press_pq_pd` (the app-layer ML-KEM-768 wrap PD, `docs/QEDOS_PRESS_PQ_WRAP.md`) links the exact
same `pg_sel4_press` staticlib as `qedos_press_pd` and therefore the exact same
`PRESS_PUBLIC_KEY` — confirmed by rebuilding a `QEDOS_PRESS_PQ=1` image (dev-key default path) and
observing it build and boot correctly. It was not given its own separate production-key wiring
because it was explicitly out of scope to touch `press_pq_pd.c` for anything beyond confirming
this; it automatically gets whatever key `qedos_press_pd` gets, since they share the one staticlib
and the one build-time-generated `press_pubkey.rs`.

**10. Secure boot and persistent (cross-cold-boot, real-hardware) rollback-prevention are
explicitly NOT verified.**
Stated plainly, not implied otherwise anywhere in this work:
- **Secure boot is not verified.** Nothing here proves the loader/kernel/initrd chain itself
  wasn't tampered with *before* `qedos_press_pd`'s signature check ever runs. That would require
  real hardware with a measured/verified boot chain (TPM-backed measurements, UEFI Secure Boot
  with a chain of trust down to the Microkit loader, or equivalent) — this project has only ever
  run under QEMU this entire session and has no such infrastructure.
- **True rollback-prevention across a real cold restart of physical hardware is not verified.**
  The generation check (#6) is a host-side file on an ordinary filesystem; it has only been tested
  surviving a *process* restart (PROD_009), not a real power-cycle of the actual production
  machine, disk failure/replacement, or an attacker with filesystem access simply deleting or
  editing `config/local/press-admin-last-generation` (which is NOT itself integrity-protected —
  it is a plain, non-secret file, and nothing here cryptographically binds its contents against
  tampering by someone who already has write access to this host's filesystem).
- **Raw `loader.img` rollback (see #6's "what this does NOT prevent") is not addressed at all.**

## What the operator does (separate machine, never this host)

```
# on the operator's OWN separate machine, with a copy of this repo and its built `qs` CLI:
python3 tools/press-sign-offline.py keygen \
    --qs PATH/TO/qs --out-seed prod-seed.hex --out-pub prod-pub.hex \
    --yes-i-am-on-a-separate-machine
# -> copy ONLY prod-pub.hex to the shared host, as config/keys/qedos-press-prod-pub.hex
# -> keep prod-seed.hex ONLY on this separate machine, forever

python3 tools/press-sign-offline.py sign \
    --qs PATH/TO/qs --seed prod-seed.hex --release N --out release.qpr CONTENT_DIR \
    --yes-i-am-on-a-separate-machine
# -> copy release.qpr to the shared host's config/local/press-inbox/, then use
#    tools/press-admin.py's /inbox page to verify-and-deploy it. QEDOS_PRESS_PROD=1 and
#    QEDOS_PRESS_PROD_PUBKEY are set automatically by accept_bundle() at that point.
```
